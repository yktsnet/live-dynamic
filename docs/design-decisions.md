# Design Decisions

実行層の設計判断の全文。要点は [README](../README.md#design-decisions) にある。

## 判定と発注を分離する

`build_signal`（判定）はブローカーに一切接続せず、`sender_gate`（発注）は判定をしない。間をつなぐのは追記専用の `signal.jsonl` だけ。判定は資格情報なしで検証・再現でき、発注だけを止める（dry_run）ことも、判定だけを回して観察することもできる。実行層のどこに問題があるかを、層の境界で切り分けられる。

## バックテストと本番を同一の判定にする

戦略判定は bt-dynamic パッケージの同じ関数を、同じ config JSON で呼ぶ。実行層に判定ロジックの複製やアレンジを置かない。

この一致は判定コードだけでなく約定条件にも及ぶ。バックテストは「指標はバー N 確定時点、エントリーはバー N+1 の open」という1本ずらしで組んであるが、これは先読みバイアス潰しであると同時に、本番では5分足が瞬時に確定しないという現実に合わせた形でもある。ずらしてあるからこそ本番は確定済みバーで判定し、次のバーの頭で発注でき、バックテストの想定とずれない。セッション終了時の強制決済（EOD）もエンジン側と同じ切り方をする。検証した式と運用する式が違えば、検証の意味がない。

## 建玉はブローカーに問う

初期実装はローカルに建玉状態（position ファイル）を持ち、オープン中はシグナルをブロックしていた。本番で分かったのは、ローカルで建玉を計算・保持するのは一見簡単に見えてロジックが難しすぎるということ（TP/SL 約定をいつ検知してクリアするか、部分約定・失敗をどう反映するか）。ブローカーに直接問う方が単純で正確である。

そこで建玉状態のローカル保持を廃止した。条件を満たしたら毎回エントリーし、ネットアウトはブローカーが処理する。OCO の配置量も送信履歴からでなく、API が返す現在の建玉から計算する。

## OCO は約定後に照合して揃える

TP/SL は「エントリーと同時に置いて終わり」ではなく、`oco_manager.ensure()` が現在の建玉と突き合わせて毎回揃える: 建玉量と合わない古い注文を取り消し、足りないブラケットだけを置き、建玉がなければ孤児注文を掃除する。配置済みであることを信じず、実行のたびに正しい状態へ収束させるため、途中失敗・レート制限・手動介入があっても次の実行で自己修復する。

## 常駐プロセスを持たない

すべてのスクリプトは systemd timer から oneshot で起動され、走り切って終了する。常駐デーモンには「死んでいるのに誰も気づかない」という状態があるが、oneshot にはそれがない（timer の `Persistent=true` が取りこぼしも補完する）。

同時実行の防御はロックでなく冪等キーで行う。発注は判定スロット（`time_utc`）、EOD は日付、キルスイッチ実行は5分スロットをキーに、処理前に既存記録と照合する。重複起動しても二度目は何もしない。

## 状態は追記専用の JSONL

シグナル・送信記録・決済記録はすべて追記専用の JSONL ファイルで、書き込みは `.tmp` → `os.replace` の atomic write。DB を持たないので、監査は `grep` と `tail` で済み、復旧は「ファイルを見る」以上のことがない。追記専用だから記録の改変がなく、冪等キーの照合台帳をそのまま兼ねる。

## 壊れ方を常に安全側に倒す

- 発注ゲートの既定は dry_run（`ENABLE_EXEC_REQUESTS=0`）。切替を忘れて動かしても「発注されない」側に倒れる
- 建玉を閉じる装置は三層（約定直後の OCO・セッション終了の EOD・外部キルスイッチ）。どれか一つが死んでも残りが閉じる
- キルスイッチはフラグファイル1行という最小のインターフェースにした。書き込むのが異常検知システムでも、深夜にエディタを開いた人間でもよい。止める手段の敷居を上げない

## ロットは連続式で「初動ほど厚く」

ロットは `LOT_BASE × (トレンド強度の直近平均 / 現在値)`。トレンド強度が低い（＝初動に近い）ほど厚く張る。初期実装は3段階のステップ関数だったが、2つの境界値と3つのロット値という調整ツマミを抱えることになるため、ツマミのない連続式に置き換えた。式は公開されるが、基準ロットと判定パラメータは外部注入である。

## 把握しきれる大きさに保つ

この実行層には前身がある。責務を細かく分解した多段パイプラインと常駐監視を備えた、機能的には完成度の高い系だったが、全体を頭に載せられなくなった時点で、直すのも信じるのも難しくなった。実弾を任せる系は、機能の網羅より「一人の人間がいつでも全体を読み切れること」を優先する——本リポの判定・発注・決済・失敗時の挙動は、コードを一晩読めば全部追える大きさに収めてある。上の各判断（分離・oneshot・JSONL・ツマミの削除）はすべてこの基準の帰結でもある。
